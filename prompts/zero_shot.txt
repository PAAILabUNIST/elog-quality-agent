Error Types to Detect

Instructions for examples
In the following Examples, each event is represented using the structure:
``` case_id, activity, timestamp, resource, error_annotation ```
- If the error_annotation field is empty, the event is clean and the recorded activity label is assumed to be correct.
- If the error_annotation field is present, it indicates that one or more errors affect the event.
- The error type(s) specify the nature of the corruption.
- The value inside parentheses always denotes the canonical (ground-truth) activity label, i.e., the label that should have been recorded without errors.
- When multiple error types are listed, they apply simultaneously to the same event.

1. Form-based Errors
Definition: Multiple events are assigned the same timestamp due to a form submission or system overwrite, even though they occurred at different real times.

Instructions:
Identify timestamp clusters within the same case
A cluster must contain at least 2 events with identical timestamps
These events must have different activity labels
All events within a cluster should be marked as form-based errors
Confidence increases with cluster size

2. Polluted Errors
Definition: Activities contain machine-generated suffixes or prefixes appended to valid activity labels, introduced by automated systems or logging tools.

Instructions:
Identify activities that contain a valid human-readable base label combined with an additional token that appears machine-generated rather than human-written
The extra token may appear before or after the base label, and may be attached using special characters such as underscore, dash, dot, slash, colon, pipe, brackets, or parentheses
The extra token may contain random alphanumeric IDs, timestamp fragments, long digit sequences, resource-like prefixes, or other system-generated patterns
Extract the base activity label by removing only the machine-generated token while preserving the meaningful activity text
Extract the likely base activity label whenever the machine-generated part can be separated or reasonably inferred from the log
Do not classify a label as polluted only because it contains punctuation, capitalization differences, or short numbers that may be part of the normal activity name
Pollution is a mechanical corruption and does not change the semantic meaning of the base label



3. Distorted Errors
Definition: Activities contain typos, character swaps, missing characters, inserted characters, internal word splits, extra spaces, or spelling errors in the base label text.


Instructions:
Apply distortion detection to the base activity label only after removing any pollution suffix or prefix
Never compare raw polluted activity strings for distortion
Identify character-level corruption: typos, swapped characters, missing characters, inserted characters, internal word splits, extra spaces, and spelling errors
Use character-level similarity such as Levenshtein/edit similarity or character n-gram similarity to compare labels against canonical forms
Distortion is about spelling corruption, not semantic variation
Do not classify semantic synonyms or paraphrases as distorted
Do not classify labels as distorted only because they are rare
Build canonical candidates from cleaned activity labels only
Do not assume that a label is clean only because it appears frequently
Do not use a fixed minimum number of canonical labels that may not fit the dataset
Do not blindly expand the canonical pool to many frequent labels when the dataset naturally contains a small activity vocabulary
Frequent distorted variants can still be distorted if they are very close to a more standard label
Compare possible canonical labels to each other; if two labels are very close at character level, prefer the more frequent and more stable label as canonical and treat the less frequent close variant as a possible distortion

4. Synonymous Errors
Definition: Two or more distinct activity label strings exist in the log that refer to the same canonical business action. Synonymy is detectable from the label text alone — the labels are near-paraphrases of each other (e.g. "assess application" and "review application" are both present in the log and mean the same thing).

Instructions:
Use sentence-transformers with model "all-MiniLM-L6-v2" to embed activity labels and detect synonyms via cosine similarity
Strip any pollution suffix from each label before embedding — never embed the raw polluted string
Encode all unique cleaned labels: model.encode(unique_labels, convert_to_tensor=True)
Compute pairwise cosine similarity: sim_matrix = util.cos_sim(embeddings, embeddings)
For each pair (i, j) where i != j, treat labels as synonyms if sim_matrix[i][j] >= 0.80
Group synonym pairs into clusters using connected components or union-find
Within each cluster, designate the most frequent label in the dataset as the canonical form
Flag all rows whose cleaned label is a non-canonical cluster member as synonymous errors
Do not flag labels that are the canonical form of their cluster
Do not flag labels that belong to no cluster (cosine similarity below 0.80 with all others)

5. Collateral Errors
Definition: Collateral errors are burst-like logging artifacts where multiple events are recorded almost simultaneously because of a logging/system issue. These events may represent duplicated or accidentally co-recorded events and do not necessarily need to have identical activity labels.

Instructions:
Go through the event log and within each case find consecutive groups of events that occur within a very short time window
Flag events as collateral if 2 or more consecutive events occur within 5 seconds, or have identical timestamps, and share strong contextual similarity such as the same resource
Activity labels do not have to be identical for collateral errors
Different activity labels can still be collateral if they appear as an implausibly close burst within the same case and resource context
Do not require exact activity-label equality as a condition for collateral detection
Do not flag repeated activities as collateral if there are normal time gaps between them
Do not flag events if different unrelated activities occur between them, because this suggests normal process progression rather than a logging artifact
The more events in the burst and the shorter the time gap, the higher the confidence

6. Homonymous Errors
Definition: The same activity label is used to represent different underlying business actions with different meanings. Differences in timing, order, resource, or surrounding activities do not constitute a homonymous error if the semantic meaning remains the same.

Instructions:
Go through the event log and find all activity labels that appear more than once within the same case. 
For each repeated label, examine the activity that immediately precedes each occurrence within the case. 
If the immediately preceding activity is consistently different across occurrences — meaning the same label is reached via completely different paths — this is a signal that the label may carry different meanings in different contexts. 
Do not flag a label as homonymous simply because it appears in cases with different outcomes or different subsequent activities — only flag when the activity itself appears to describe a genuinely different action.
When a repeated label could be either collateral or homonymous, prefer collateral if the occurrences are 3 or more, and prefer homonymous only if exactly 2 occurrences exist with clearly different preceding context
Multiple Errors
CRITICAL: A single row can have multiple error types simultaneously. Error types operate on independent layers:
Temporal structure: form-based (timestamp collisions)
Mechanical suffix: polluted (machine-generated suffixes)
Base-text quality: distorted (typos, character corruption)
Semantic meaning: synonymous (different wording, same meaning)
Duplication: collateral (logging artifacts)
Identifier noise: homonymous (same label, different meanings)


Instructions:
Check each error type independently
Never infer one error type from another
Never collapse multiple error types into one
Accumulate all detected errors for each row
Combine error types in detected_pattern_types using pipe separation
